## 一、优化路线总览

```
路线 A  核心链路闭环   ── 合成/成本/口型/分发从「有接口」到「真产出」
路线 B  成本可观测     ── 让每一次 AI 调用都记账，预算可设、超支可拦
路线 C  任务系统可靠性 ── Worker 长任务不阻塞、失败可重试、状态可追踪
路线 D  安全加固       ── 密钥隔离、Token 治理、限流分级、安全响应头
路线 E  性能与扩展     ── 分页、索引、并发控制、图片优化、N+1
路线 F  工程化         ── Docker/CI、可观测、测试、依赖治理、死代码清理
路线 G  API 契约与类型 ── 魔法路由、返回结构统一、`any` 治理
路线 H  产品体验       ── 流式反馈、时长单位、批量并发、差异化
```

优先级标注：🔴 P0（阻塞上线）· 🟡 P1（上线前应做）· 🟢 P2（上线后迭代）· 🔵 P3（长期竞争力）

## 路线 A：核心链路闭环

### A-1 🔴 FFmpeg 真实合成（当前最大产品缺口）

- **现状**：`compose.service.ts:29-57` 仅返回 `{ status: 'ready', message: '合成计划已就绪，等待 FFmpeg Worker 执行' }`，无任何实际合成。用户走完整个创作流程，最终拿不到视频文件。
- **优化动作**：
  1. 引入 `fluent-ffmpeg` + `ffmpeg-static`（或服务端安装 ffmpeg），将 `shots` 的 `resultUrl`/`videoUrl`/`audioUrl` 拼接为最终 MP4。
  2. 合成走 BullMQ 独立队列 `compose`（与 `generation` 队列隔离，避免阻塞生成任务）。
  3. 支持：多分辨率（1080p/720p）、多格式（mp4/mov）、字幕烧录（读取 `Shot.params.subtitle`）、横竖画幅（`project.aspectRatio`）。
  4. 产物上传 MinIO 后返回 presigned URL，并更新 `Project.status = 'completed'`。
- **投入**：2–3 天。**收益**：产品从「演示」变「可用」，唯一能交付成片的环节。

### A-2 🔴 成本统计接入真实调用链路

- **现状**：`cost.service.ts:22` 定义了 `recordCost`，但全仓库 `recordCost(` 只有定义、**零调用**。`UserApiKey.totalCalls/estimatedCost` 永远为 0，成本面板形同虚设。
- **优化动作**：
  1. 在 `generation.worker.ts` 的 `processJob` 成功/失败分支调用 `CostService.recordCost`，按能力记录 tokens/duration/imageCount 与 cost。
  2. 同步在 `storyboard.service.ts`（LLM 分镜）、`storyboard-tts.service.ts`（TTS）、`character-library.service.ts`（角色图）等**直接调用 Adapter 的同步路径**也记账——目前记账只应挂在 worker，但大量 LLM 调用是同步直连的。
  3. 成本单价从 `AIModel.billingRule` 读取，而非硬编码。
- **投入**：1–1.5 天。**收益**：成本面板真实可用，为 B 路线的预算守卫打基础。

### A-3 🟡 口型同步从「规则假实现」升级为「可选真实方案」

- **现状**：`lip-sync.service.ts` 用「汉字 Unicode 编码 % 20 估算笔画数」来猜口型，属于占位实现，实际不可用于成片。
- **优化动作**（分级）：
  - 短期：明确标注为「预览/占位」，前端不误导用户可导出。
  - 中期：接入真实 viseme 能力（如 Rhubarb Lip Sync 服务、或视频模型自带的口型同步参数）。
  - 将 `mergeToVideoParams` 的结果真正喂给视频 Adapter，而非仅生成 JSON。
- **投入**：取决于选型，1–3 天。**收益**：差异化功能真实落地。

### A-4 🟡 多平台分发包真实导出

- **现状**：`distribute.service.ts` 只做「校验 + 生成建议」，`exportDistributePackages` 不产出任何文件/裁剪/改画幅。`validateConfig` 通过 `/projects/0/...` 魔法路由访问（见 G-1）。
- **优化动作**：导出时按平台 `aspectRatio` 调用 FFmpeg 裁剪/加黑边/缩放，生成各平台成片 + 标题描述 JSON。
- **投入**：2 天。**收益**：P3 差异化「多平台分发」兑现。

## 路线 B：成本可观测与预算守卫

### B-1 🔴 记账点全覆盖 + 单价来自模型配置

- 见 A-2，但这里强调**记账点必须覆盖同步 LLM 调用**。当前 `storyboard.service` 的「AI 分镜生成」「脚本审计」「小说拆分」都是直接同步调 DeepSeek，这些调用**既不经过 BullMQ、也不记账**，是成本黑盒。
- **建议**：抽一个 `BillingInterceptor` 或 `withCost(record, fn)` 包装器，在所有 Adapter 调用入口统一记账，避免散落。

### B-2 🟡 预算守卫（用户可设月预算，超支拦截）

- **现状**：`UserApiKey` 无预算字段；用户可用自己的 Key 无限烧钱，平台无法在超支时提醒。
- **建议**：`AIModel` 或 `UserApiKey` 增加 `monthlyBudget`，worker 执行前查询当月累计成本，超支则任务直接标记 `blocked` 并推送通知。产品文档已把「预算守卫」列为 P2，需提上日程。

### B-3 🟡 成本归因粒度到「项目 × 阶段 × 模型」

- **现状**：`CostService.getProjectCostSummary` 用 `estimateTaskCost` 的**硬编码单价**（0.07/0.15/0.70/0.03 元）估算，且读取 `task.parameters?.billingRule`（该字段实际不存在，billingRule 在 `AIModel` 上）。数据失真。
- **建议**：新增 `CostLog` 表（或复用 `GenerationTask` 增加 `cost` 列），记录真实 cost，替代运行时估算。

### B-4 🟢 成本面板实时刷新

- **现状**：成本面板依赖 React Query 手动刷新，无 WebSocket 联动。
- **建议**：任务完成时通过已有 `task:progress` 事件同时刷新成本查询。

## 路线 C：任务系统可靠性

### C-1 🔴 视频长轮询阻塞 Worker 槽位

- **现状**：`doubao-video.adapter` 的 `pollTask` 在 Worker 内同步轮询最长 5 分钟；`generation.worker.ts` 全局 `concurrency: 2`。两个视频任务即可占满所有 Worker 槽，导致图片/TTS 任务排队饿死。
- **建议**：
  1. 按 capability 拆队列：`generation:image`、`generation:video`、`generation:tts`，各自独立 Worker 与并发。
  2. 视频改为「提交任务 → 记录 provider taskId → 定时重入队轮询」的异步模式，Worker 不长期占用。
  3. 视频轮询超时返回 `{ status: 'processing', taskId }` 而非抛错（呼应 08-04 BIZ-5）。

### C-2 🟡 失败重试无业务级幂等与死信

- **现状**：Queue 有 `attempts: 3` + 指数退避，但 `processJob` 失败直接 `throw`，无幂等键、无死信队列、无人工重试入口（`GenerationTask.retryCount` 已建但未消费）。
- **建议**：为 job 加 `idempotencyKey`（taskId）；`removeOnFail` 改为移入 `failed` 集合，提供「重试」API 供前端调用。

### C-3 🟡 Worker 无 TTL / 无优雅关闭 / 无并发上限配置化

- **现状**：`concurrency: 2` 硬编码；`onModuleDestroy` 只 `close()`，未处理进行中任务的 drain；无 `timeout` 配置，卡死的 provider 调用会永久占用槽位。
- **建议**：并发数走 env；job 加 `timeout`；进程监听 SIGTERM 优雅 drain。

### C-4 🟢 Worker 状态回写与 WebSocket 推送去重

- **现状**：`processJob` 完成/失败均直接写库 + 推送，但无「进度 10→100」中间推送（`updateProgress` 只更新 BullMQ 内部进度，未推到前端）。前端进度条只能看到 0→100。
- **建议**：在 worker 各阶段 `emitTaskProgress` 中间进度（提交中/生成中/上传中）。

## 路线 D：安全加固

### D-1 🟡 AES 密钥与 JWT 密钥彻底分离

- **现状**：`crypto.service.ts:11` 仍 `AES_KEY || JWT_SECRET` 回退。虽已消除硬编码弱密钥，但两把密钥复用同一秘密仍违背最小权限——JWT_SECRET 泄露即等于所有用户 API Key 泄露。
- **建议**：删除回退，`AES_KEY` 缺失时启动即失败（`main.ts` 已对 JWT_SECRET 这么做了，对 AES_KEY 也应一致）；AES_KEY 需 base64/hex 解码后校验长度 ≥ 32 字节。

### D-2 🟡 Token 存储从 localStorage 迁到 httpOnly Cookie

- **现状**：`lib/api.ts:9` 从 localStorage 读 token；任何 XSS 即可窃取。08-04 SEC-5 已列，仍未改。
- **建议**：短期加强 CSP（禁内联脚本）；中期改用 `httpOnly + Secure + SameSite` Cookie，配合 CSRF 防护（或保留 Bearer 但缩短有效期 + refresh token）。

### D-3 🟡 全局限流粒度过粗，且误伤正常使用

- **现状**：`app.module.ts:28-31` 全局 `ThrottlerModule` 30 次/分钟。SPA 一屏可能发起数十个 GET（项目列表、角色、分镜、模型…），30/min 极易误伤正常浏览；而「视频生成」这类昂贵接口与「读列表」同限。
- **建议**：分级限流——读接口放宽（如 300/min），写/生成接口收紧（如 10/min），并配 `@Throttle()` 装饰器按路由覆盖。

### D-4 🟡 缺安全响应头 / CORS 单点

- **现状**：`main.ts` 无 `helmet`；CORS 只允许一个 `FRONTEND_URL`。
- **建议**：接入 `helmet`；CORS origin 支持白名单数组；对登录/注册等敏感接口加 stricter 头。

### D-5 🟢 Worker 侧 `resolveApiKeyById` 无用户归属校验

- **现状**：`models.service.ts:316` 按 `apiKeyId` 直查，不校验 userId。worker 的 job data 若被伪造 apiKeyId，可跨用户读取他人密钥（服务端内部攻击面，风险中等）。
- **建议**：`GenerationJobData` 已含 `userId`，`resolveApiKeyById` 增加 `userId` 参数做归属校验。

## 路线 E：性能与扩展

### E-1 🟡 列表接口全量返回、无分页

- **现状**：`listProjects`、`listMyApiKeys`、`listEpisodes`、`listModels`、角色库、模板列表均 `findMany` 全量返回。项目/角色/分镜数量增长后前端列表会越来越慢。
- **建议**：统一 `{ page, pageSize, total, items }` 分页契约；前端 React Query 接无限滚动或分页器。

### E-2 🟡 前端批量生成无并发控制（呼应 08-04 BIZ-1，仍未改）

- **现状**：`generate/page.tsx` 批量生成 `forEach` 同时触发，20 镜 = 20 个并发请求，打满配额且无整体进度/取消。
- **建议**：串行或 `p-limit(3)` + 整体进度条 + 取消；后端 worker 本身已有并发，前端不必雪上加霜。

### E-3 🟡 图片未走 Next/Image 优化 + 缺 remotePatterns 精确化

- **现状**：多处 `<img>`；`next.config.mjs` 用 `*.amazonaws.com` 通配（08-04 SEC-11）。
- **建议**：配置精确 remotePatterns，外部图统一 `<Image>`；MinIO 图走 presigned URL 时注意缓存头。

### E-4 🟢 数据库索引与 JSON 字段

- **现状**：`GenerationTask` 按 `projectId`、`status` 高频查询；`Shot` 按 `projectId`/`storyboardId`；`AIModel.capability` 用于筛选。关系字段有隐式索引，但 `status`、`capability` 等无显式索引。`Shot.params`、`Character.variants/viewImages` 等 JSON 字段无 schema。
- **建议**：为高频过滤字段加索引；JSON 字段用共享 TypeScript 接口 + 读取时 Zod 校验（与 08-01 第五部分一致）。

### E-5 🟢 N+1 查询与快照膨胀

- **现状**：`ProjectVersion.snapshot`、`Template.snapshot` 存完整项目快照（`Json`），版本越多体积越大，`restoreVersion` 直接全量覆盖。
- **建议**：快照做差异化存储或压缩；版本列表只取元数据（已实现），详情懒加载。

## 路线 F：工程化与可维护性

### F-1 🔴 无容器化 / 无一键启动 / 无 CI

- **现状**：项目依赖 MySQL + Redis + MinIO 三个外部服务，但仓库**无 Dockerfile、无 docker-compose、无 CI 配置**。README 要求开发者手动装三件套，Redis 版本还要求 ≥ 5.0（README 已标注本地是 3.2.100）。
- **建议**：
  1. 提供 `docker-compose.yml` 一键拉起 MySQL/Redis(≥5)/MinIO + api + web。
  2. GitHub Actions：lint + typecheck + test + build（前后端各一个 workflow）。
- **投入**：1 天。**收益**：消除环境差异，新人 5 分钟跑起来。

### F-2 🟡 后端 package.json 混入前端依赖

- **现状**：`ai-video-api/package.json` 仍含 `@radix-ui/*`、`framer-motion`、`react-hook-form`、`zustand`、`tailwind-merge`、`@tanstack/react-query`、`@dnd-kit/*`、`clsx` 等前端库（08-01 P2-4 仍未清）。
- **建议**：彻底清理；用 `depcheck` 定期扫未用依赖。

### F-3 🟡 测试脱节 + 无前端测试

- **现状**：后端 `storyboard.service.spec.ts` 编译报错（类型不匹配），e2e 只有 auth 一例；前端**无任何测试**（无 jest/playwright/vitest）。
- **建议**：先修绿现有测试，再为核心链路补单测；前端对「登录 → 建项目 → 生成分镜」关键路径加一条 Playwright E2E。

### F-4 🟡 死代码与遗留文件

- **现状**：`workers/image.worker.ts`、`workers/video.worker.ts` 定义了 `ImageWorker`/`VideoWorker`，但 `queue.module.ts` 只注册了 `GenerationWorker`——这两个是**死代码**，与真实实现并存易误导。
- **建议**：删除或并入 `GenerationWorker`；`docs/archive/` 与 `.agents/`、`skills-lock.json` 等非代码文件清理归类。

### F-5 🟡 可观测性缺失（日志无关联、无指标、无追踪）

- **现状**：有 Winston 日志 + 请求日志中间件，但**无 requestId 贯穿**、无结构化 JSON 日志、无 Prometheus 指标、无 APM。排查一条「任务为何失败」要人肉对时间戳。
- **建议**：
  1. 中间件生成 `requestId` 并注入日志上下文。
  2. 日志结构化（JSON），保留 traceId。
  3. 引入 `prom-client` 暴露 `/metrics`（任务队列深度、成功率、耗时、AI 调用成本）。

## 路线 G：API 契约与类型治理

### G-1 🔴 `/projects/0/*` 魔法路由

- **现状**：`getVariantTypes`（`/projects/0/characters/variant-types`）、`getPlatforms`/`getPlatform`（`/projects/0/compose/distribute/...`）、`validateConfig`（`/projects/0/...`）用 `0` 作为「全局资源」占位，语义混乱且部分绕过了资源归属语义。
- **建议**：改挂到 `/meta/...`、`/models/variant-types`、`/distribute/platforms` 等独立路由，语义清晰、鉴权一致。

### G-2 🟡 返回结构不统一（`data` 包裹不一致）

- **现状**：有的接口返回 `{ data: X }`，有的直接返回 `X`；前端 `lib/api.ts` 里 `.then(r => r.data)` 与 `.then(r => r.data.data)` 混用，`getModel` 甚至把 `{ data: model }` 当 `AIModel` 用（`lib/api.ts:266`）。
- **建议**：后端统一 `{ data: T }` 包裹（或统一裸返回），前端封装一个 `unwrap<T>(promise)`，并让后端用 NestJS Interceptor 统一包一层，避免手写不一致。

### G-3 🟡 `any` 泛滥 + Prisma JSON 无类型

- **现状**：`lib/api.ts:1` 全局 `eslint-disable no-explicit-any`，685 行几乎全 `any`；后端 JSON 字段读写作 `as any`。
- **建议**：分三批治理——① 定义 `Shot.params`、`Character.viewImages/variants`、`ModelPreference.defaults`、`GenerationTask.result` 共享类型；② 前端 `lib/api.ts` 拆 `types/*.ts` 并全量补返回类型；③ 删掉全局 disable。

### G-4 🟢 前后端 DTO 字段不一致

- **现状**：`UpdateModelPreferenceDto` 与前端 `setPreferences` 参数、`Shot.duration` 单位（前端秒 vs 后端毫秒）、`ComposeResult` 形状等（08-01 第五部分已列，仍存在）。
- **建议**：引入 OpenAPI 生成前端类型（NestJS 已有 Swagger，可用 `openapi-typescript` 生成 `api-types.ts`），从根上消除手工同步漂移。

## 路线 H：产品体验与差异化

### H-1 🟡 长任务无流式/进度反馈

- **现状**：LLM 分镜生成 30s+，前端只有按钮 loading，无流式；TTS、视频生成进度只有 0/100 两态。
- **建议**：分镜生成改 SSE 流式；视频/TTS 用 C-4 的中间进度推送。
